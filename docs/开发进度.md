## 十一、验收自动化（v0.2.3）

**问题**：渲染期异常、重生渲染器、开局盾条不显示这类缺陷全部"只有真的点进去才发现"；人工逐屏截图能发现，但结论不会自动复现，CI 只跑 typecheck + 单测，UI 崩了照样出包。

**做法**：`tests/ui-smoke.test.ts` 用 jsdom（vitest 的官方可选 peer，仅 dev 依赖——运行时依赖仍为零）启动真实应用并用真实点击走完流程。**刻意不引入 Playwright**：要防的缺陷是渲染期 JS 异常与 canvas 行为，jsdom + 桩化 canvas 就能抓到，不值得为此引入浏览器下载与额外 CI 时长。

**两个关键点（改这个文件前先读）**：
1. **`render()` 自带兜底会吞掉异常**（捕获 → 重置续档 → 回主菜单 → toast「存档数据异常」）。所以桩写坏或真的崩了都**不会**让测试抛异常，只会静默退回菜单。断言必须两件一起做：该屏类名在场 **+ 页面上没有那句兜底 toast**。少了后者等于没测。
2. **canvas 桩按渲染器实际调用面精确实现，是有意的契约**：将来渲染器调用新的 canvas 方法而桩里没补，冒烟会以 TypeError 失败（提示来补桩），而不是被静默略过。必须返回值的只有 `getContext`、`createLinearGradient`/`createRadialGradient`（需 `addColorStop`）、`measureText`（需 `width`）；`globalAlpha` 会被读取并参与乘法，必须给数字。

**变异验证（证明它真能抓到）**：①在 `renderPrep` 里抛异常 → 冒烟失败并报「渲染触发兜底，应用被重置回主菜单」②把桩的渐变改成返回 `undefined` → 战斗路径失败 ③让 `writeSave` 失效 → 报「备战期应写入续档」。

**边界（不要误读）**：jsdom 抓不到真实排版、字号、溢出与画布实际绘制内容——那些仍靠发布前的人工逐屏截图验收（§九）。**"冒烟过了"不等于"视觉没问题"。**

## 十、v0.2.2 深挖审计与修正清单

三路独立审计（战斗引擎 / 对局与存档 / 渲染与 UI）→ **每条高优结论都回代码复核**（结论未经验证不改），逐条修正并配可捕获的测试。

**引擎（都会改变实战强度）**
1. 团队暴击双计：`battle-build` 烘了 `+tf.critRate`，`dealDamage` 又加一次（后台单位未烘，可作对照证明是不一致）→ 编译层只留基础暴击

3. 景元「神君」整局只触发一次：`shenjunStacks` 只设不增、`ultGain`/`max` 零读取（终结技文案却写着「神君 +2 层」）→ 按 `ultGain` 叠层封顶 `max`

**对局与结算**
5. 输掉末位面首领被判通关（`advanceNode` 只看节点走完）→ 白送晋升 +1~3、`totalWins++`、解锁超频。现失败即判对局结束
6. 牌池只减不增：卖出/卖光策略不返还，而重摇的未购商品会返还 → 角色会被抽干、3★ 不可能。新增 `returnToPool`/`takeFromPool`，按 `3^(星−1)`（合成不改变占用量）统一口径，所有增删路径统一走这对出入口
7. 四费晋升 + 满备战席溢出到第 10 格：`willMerge` 按 1★ 预判而实际以 2★ 入席 → 按实际入席星级预判

**存档与可用性（P0 级可用性缺陷）**
8. `shop`/`pool`/`slot`/`seq`/`strategyData|environmentData` 值/`exp`/布尔字段此前完全不校验：商店坏→备战界面直接白屏；牌池坏→商店永久空或 reroll 崩；非法 slot→棋子看不见点不到卖不掉却仍占上阵数与羁绊、出战永久失效；重复 uid→卖一个删两个；计数器 NaN→金币 NaN（无限白嫖）或战斗 NaN（全场必败）；`exp:999`→一次买经验满级；`"false"`→超频等开关反转
9. 选择节点软锁：空三选一/空奖励的存档既打不了也推进不了（旧迁移把空三选一回退成 prep 却停在原节点）→ 载档后 `repairPhase` 按节点重进阶段（能重摇就重摇，保留选择权；无可选才跳过）
10. 渲染异常无兜底：任何异常都留下空白舞台且无恢复入口 → 捕获后 `discardCurrent` 重置当前对局回主菜单（终身统计保留），兜底在 `render()` 内部所以调用方不会漏
11. 战斗中重绘会并存两个渲染器：`renderBattle` 无重入保护，战斗中触发重绘时旧实例不被销毁，其动画循环对着已卸载的画布持续运行、并多跑一次完整模拟（CPU/电量浪费）。现模块级 `activeRenderer` 先销毁旧实例 + 结果卡结算幂等；`destroy()` 同时清掉未触发的 60ms 结算回调。**更正**：原先记录为"双重结算（双扣血双推进）"，实测不带守卫时中途重绘并打完**结算次数仍为 1**（结果卡每次重建、DOM 里只有一个「继续」按钮，不存在双结算路径）——这条的实际收益是消除泄漏与重复模拟
12. 开局护盾不显示：`start.shieldPct` 无消费者，护盾流要等首次受击 → `applyStart` 按比例初始化盾条

**渲染性能（实测：静态层约占每帧填充像素 95%）**
13. 夜空/星点/竞技场地台/9 条射线/5 条弧/半场辉光每帧重新光栅化（≈9.5M 设备像素/帧）→ 构造期预渲染一次，每帧一次 `drawImage`；画布位图改按 `min(1, 显示比例)×dpr`（1280 视口实测位图 1280×599，与 CSS 1:1）；特效数组先判空、行动条名字截断记忆化

**类型与真值单一化**
14. 拆 `AppCtx`/`GameCtx`：菜单/图鉴在类型层读不到对局状态（此前 `st: null!` 且 `goMenu` 不清，菜单能读到已脱离存档的旧状态）；`PendingReward` 改判别联合；`h()` 泛型化；星级倍率/可用性判定/奋斗协议代价/等级不足提示/利息与商店容量（后两者原为**值为错的死配置**）各自单一来源
